## Hash-changing releases (`definitionHash`, RFC-0008)

`definitionHash` parses the document with `WorkflowDefinitionSchema` before canonicalising it, so every resolved schema default is part of the hash whether the author wrote it or not (`execution.concurrency`, `execution.timeoutMs`, `description: ''`, `edges: []`, trigger defaults such as `signature: 'hmac_sha256'` and `inputPointer: '/body'`, variable `source: 'definition'`, secret `required: true`, …). Consequently:

- Changing **any default** in `packages/workflow-core/src/{policy,definition,nodes}.ts` (or adding a defaulted field to a schema the hash covers) changes the hash of every stored definition that omitted it. Such a change is a **hash-changing release** of `@flowaid/workflow-core`: it needs a minor version bump, an entry in this section and a reviewed update of the golden constants in `packages/workflow-core/src/fixtures-roundtrip.test.ts` (`GOLDEN_HASHES`) — the test fails until the new hashes are pinned, which is the point.
- Consumers (`workflow_versions.definition_hash`, plan caches, the CLI's "unchanged" check) must treat a hash computed by a different `@flowaid/workflow-core` version as incomparable and recompute rather than diff.
- `layout` and `metadata` never affect the hash; key order and node/edge order never affect it; duplicate node or edge ids throw a `TypeError` instead of hashing.
