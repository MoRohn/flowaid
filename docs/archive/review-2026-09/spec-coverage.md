## Findings (detail)

See the structured output for the canonical list. Each finding below carries the evidence and the concrete change.

### F1 Smart model routing / cost optimizer / generation failover (high, L)

`ModelRefSchema = { provider, model }` (CONTRACTS.ts:492); `FailoverChain` and `HealthTracker` apply only to decisions (§6.2); `PROVIDER_FAILOVER` never fires for `flowaid.ai.generate`; "cost optimizer / smart routing" is a single clause in WP-27. Design: `GenerationPolicySchema { candidates: ModelRef[] (ordered, 1–5), strategy: 'ordered' | 'cheapest' | 'fastest' | 'healthiest', requirements: { tools?, jsonSchema?, vision?, minContext? }, maxCostUsdPerCall? }` accepted wherever a `model` widget is today (`x-ui.widget: 'model'` grows a "fallbacks" list); `ProviderRegistry.generation(policy)` returns a `FailoverChain<GenerationProvider>` that filters candidates by `ModelInfo.capabilities`, orders by strategy using `HealthTracker` (skip `down`), `ModelCatalog.price()` and the p95 window, and records `attempts[]` + `PROVIDER_FAILOVER` exactly as decisions do; compiler `W_FAILOVER_UNCONFIGURED` extended to generation. Cost optimizer: new package `packages/advisor` (deps: workflow-core, workflow-compiler, providers, evaluation types) with `optimize(plan, stats: NodeStats[], catalog, evalReport?) → Suggestion[]`, where `Suggestion = { nodeId, kind: 'cheaper_model' | 'batch_decisions' | 'cache_safe_node' | 'tighten_bounds', estimatedSavingsUsdPerRun, risk, fix: JsonPatch[] }`; served by `POST /v1/workflows/:id/optimize` (uses `node_runs` aggregates over 30 d) and shown in the Problems panel as `I_COST_SUGGESTION` with quick-fix; feature flag `advisor`.

### F2 AI builder and AI critic (medium, L)

UI.md §1 already renders "AI builder (when enabled)"; API/ARCH only say "later". Design: `POST /v1/workflows/ai/generate { prompt, baseDefinition?, catalogFilter? }` → `{ definition, diagnostics, rationale, iterations }`: structured generation against `z.toJSONSchema(WorkflowDefinitionSchema)` (compact variant: compact refs, layout omitted) with the manifests of the allowed nodes in the system prompt, then a repair loop (≤ 3) feeding compiler diagnostics back until zero `E_*`; result is saved as a draft only after the user accepts. `POST /v1/workflows/:id/ai/critique { definition? }` → `Advice[]` (`{ code, severity: 'advice', nodeId?, message, fix? }`) computed by deterministic rubric rules first (unbounded loop with LLM inside, irreversible tool after a decision with no confidence gate, PII input flowing into a generation prompt without `redactFields`, no evaluation set linked, no failover on the primary decision hop, `W_COST_ESTIMATE` above workspace budget) and an optional judge pass through the workspace decision chain for "likely to fail in production" (boolean) with reasons. Both live in `packages/advisor`, gated by `features.ai_builder`; Playwright covers "AI builder → accept → compile zero errors".

### F3 Consensus and Validator nodes are one-liners (medium, M)

ARCHITECTURE.md:682 is the only definition. Specify `flowaid.decision.consensus`: config `{ question: DecisionQuestion, voters: ProviderHop[] (2–5, distinct), method: 'majority' | 'confidence_weighted' | 'unanimous', minAgreement: number ∈ [0,1] (default 0.6) }`, input `state`, output `decision` (`DecisionResult` with `provider: 'consensus'`, `model: 'consensus:v1'`, `probabilities` = confidence-weighted mean of voter distributions renormalised, `confidence = agreement × mean(voterConfidence)`, `raw.votes: DecisionResult[]`, `attempts` = concatenation), control-outs `agreed` / `disagreed`; each vote is its own `DECISION_REQUESTED/COMPLETED` sharing `batchId = nodeRunId`; excluded from compiler batch groups; `E_DECISION_CONFIG` when voters < 2 or repeated hop; cost = Σ votes. `flowaid.decision.validator`: inputs `value` (any) + optional `reference`; config `{ rubric: string, criteria?: {true,false}, threshold: number }`; output `decision` (boolean) + `value` pass-through; outs `valid` / `invalid`; UI shows it as a decision card. Add both to WP-12 tests and to `fixtures/manifests`.

### F7 Schedules have tables and routes but no scheduler (high, M)

No component computes `schedules.next_run_at`; no cron parser is pinned in VERSIONS.md; misfire/catch-up, jitter and `lastError` are undefined; definition `triggers[]` of type schedule/webhook/mcp are never reconciled into `schedules`/`webhooks`/`mcp_exposures` rows (only `E_TRIGGER_CONFLICT` exists). Design: pin `croner` 9.x; worker `jobs/schedule.ts` polls every 15 s `SELECT … FROM schedules WHERE enabled AND next_run_at <= now() FOR UPDATE SKIP LOCKED LIMIT 20`, locks the row, creates the run with `origin: 'schedule'` and `idempotency_key = 'schedule:<id>:<fireAtIso>'` (replicas cannot double-fire), applies `overlap: 'skip'` by checking `last_run_id` non-terminal, computes the next fire in the schedule's timezone; new columns `catch_up ('skip'|'one'|'all')`, `max_catch_up`, `jitter_ms`, `last_error`; audit `schedule.fired`. Reconciliation rule in API.md §3.3/§3.9: on `PUT /deployments/:env` the definition's `triggers[]` are upserted per environment keyed `(workflowId, environmentId, triggerIndex)`, removed triggers are disabled (not deleted), and the response lists the resulting webhook URLs / schedule ids.

### F8 Webhook inbound dedupe (medium, S)

API.md §6 relies on `X-Timestamp` ± 5 min only when present; providers such as GitHub redeliver with a stable delivery id. Add `webhooks.idempotency_header` (e.g. `X-GitHub-Delivery`), `webhook_deliveries.external_id` with a unique index `(webhook_id, external_id)`; a repeat returns `200 { run_id }` of the original delivery; missing header falls back to sha256(raw body) within a 24 h window; audit `webhook.duplicate`.

### F9 `sensitive`/`containsPII` privacy flags have no semantics (medium, S)

`PrivacyPolicySchema` (CONTRACTS.ts:470) carries four flags; §10.6 defines effects only for `doNotPersist`, `redactFields` and `x-dataClass`; `runs.privacy` and `runs.data_class` overlap with no derivation rule. Define: `containsPII: true` ⇒ the node's whole input/output is treated as `x-dataClass: pii` (masked at write, 7 d I/O retention); `sensitive: true` ⇒ hashed at write, excluded from exports, `add-to-evaluation`, external review context and `NodeRunDetail` for non-admins; run-level `privacy` = OR over executed nodes and the input schema classes, `runs.data_class` = max class seen; `GET /v1/runs?privacy=pii|sensitive` filter; UI chip on the run row; `E_DONOTPERSIST_SIDE_EFFECT` stays.
